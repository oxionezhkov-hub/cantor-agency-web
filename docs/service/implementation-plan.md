# План самостоятельной разработки Cantor

Рабочая ветка: `service-shell-dashboard`, [PR 328](https://github.com/oxionezhkov-hub/cantor-agency-web/pull/328). Пользователь разрешил дорабатывать сервис, регулярно проверять и исправлять ошибки, публиковать отдельное облачное превью и сообщать Олегу через управляющего Telegram-бота. Мерж и выкладка `main` в эту работу не входят.

## Источники перед реализацией

- [ТЗ и согласованные решения](specification.md), [диалоги и база знаний](dialog-policy.md), [журнал проходов](WORKLOG.md).
- `avito-tasks`: личные приглашения и роли, назначенные клиенты, задачи/уведомления, смена статусов и координация команды.
- `avito-bids`: таблицы, фильтры, массовые операции, состояния «в очереди» и «применено», расписание и фактическая ставка.
- `avito-ai-sales`: разделение списка и чата, черновика/отправки, базы знаний и фактов преподавателя, тёмная тема.
- `_worker.js`: реальная маршрутизация, права, контуры KV, команды бота, фоновые задания и адаптеры Авито; не доверять старой шпаргалке вместо текущего обработчика.
- `yc-dashboard-api-proxy`: ограничения путей и доставка из РФ. Наличие прямого Cloudflare URL не доказывает доступность у всех клиентов.
- `dashboard-old`, `finance`, `base`, `fonts/fonts.css`: существующие сценарии команды, методика и визуальная система.

## Визуальная система

Главный референс — существующие приложения Cantor. Локальный навык UI/UX использован для проверки взаимодействий и адаптивности; его автоматически предложенные детские шрифты/синяя палитра не применяются, поскольку не соответствуют бренду и взрослой аудитории репетиторов.

Сохранять Geologica для интерфейса, Unbounded для бренда/крупных заголовков, фон `#F4F3F0`, белые поверхности, акцент `#E8391D`, линии `#E5E2DD`, радиусы около 10–14 px. По последнему указанию владельца интерфейс только светлый; тёмную тему, футер, хлебные крошки, повторные заголовки и демо-примечания не возвращать. Статус сообщается текстом, клавиатурный фокус видим, области касания от 44 px; основной текст не мельчить ради плотности.

## Текущий приоритет владельца

После замечания «зачем доступы, если внутри ничего не готово» серверные доступы и provisioning отложены. Сначала доводить продуктовые сценарии внутри: обращение, переписка/черновик, запись/перенос, исход встречи, оплаты и связанный обзор. Не возвращаться к инфраструктуре вместо пользовательских действий. Следующий шаг после единой карточки — удобное редактирование собственного расписания и обработка обращений по базе знаний.

## Порядок проходов

1. **Воспроизводимость и доставка:** установка по lockfile, типы/линтер, тесты, отдельная SPA-сборка и облачное превью, Telegram-уведомления. Снять исходные ошибки полного тестового набора, не выдавать выбранные успешные тесты за полностью зелёный набор.
2. **Рабочая оболочка и обзор:** навигация, только светлая тема, мобильный экран, смысл показателей, состояния источников и глубокие ссылки. Убрать выдуманные нормативы из демо и связать действия с объектами.
3. **Предметная модель:** независимые сущности заявки, ученика, диагностики, платежа; дедупликация и правила показателей; серверный контракт и тесты прав/конфликтов. Не называть localStorage серверным хранением.
4. **Диалоги и расписание:** ручной режим по умолчанию, согласованные исключения, переход на ИИ по согласованию при вмешательстве человека, окна/перенос/исход, правила базы знаний. Поддержка Cantor остаётся живой в Telegram.
5. **Подписка и данные:** месяц с даты оплаты, автопродление, отключение следующего продления без заморозки; возврат только администратором; история доступна после окончания, новых подтягиваний нет. Реальную оплату не подменять визуальным переключателем.
6. **Приёмка:** проверки 390/1440 px, сценарии ТЗ, сверка связанных экранов, повторный проход по превью, итог с доказательствами и известными ограничениями.

Время отдельных шагов не является обещанием реализации всей серверной платформы за один проход. На каждом запуске делать законченный приоритетный срез, исправлять найденные ошибки и передавать результат следующему проходу через WORKLOG.

## Проверки

Из `service-shell`:

- `npm ci --cache /tmp/cantor-npm-cache`
- `npm run typecheck`, `npm run lint`
- `npm run test:service` — предметные тесты; правила согласованы с базой; CRM-модель и локальный адаптер также входят в полный npm test.
- `npm run test:service:server` — SQL/HTTP, изоляция клиента, конкурентная запись, повтор запроса, роли и сохранение после открытия базы заново.
- `node --test scripts/ops/*.test.mjs` — изоляция превью и адресность/подпись уведомлений.
- `npm test` — полный исходный набор, включая унаследованные тесты упаковки Grok. Переносимость исправлена: четыре проверки внешней документации упаковки явно пропускаются только при отсутствии исходного Grok skill; полезные проверки приложения остаются активными.
- `npm run build:preview` — без миграций, с деморежимом в технических метаданных, без плашек в UI.
- `node scripts/ops/crm-browser-check.mjs <URL>` — запись/отмена/перенос, исход встречи, оплаты с копейками, повторные оплаты, сохранение и две вкладки на 390/1440 px.
- `node scripts/ops/browser-check.mjs <URL> <каталог-в-tmp>` — шесть разделов, обе ширины, светлая тема даже при старой настройке dark/перезагрузка, отсутствие ошибок JS и переполнения страницы.

## Одновременные проходы

Перед изменениями проверить `git status`, последнюю ревизию ветки и актуальный WORKLOG. В общей среде использовать атомарный каталог `/tmp/cantor-service-work.lock` с owner.json и временем начала; активный проход не затирать и второй редактор не запускать. Если блокировка старая, сначала проверить процессы/состояние, а не безусловно удалять. Незакоммиченные изменения другого прохода сохранять. Не использовать force push.
