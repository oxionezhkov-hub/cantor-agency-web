# Серверный срез CRM

Реализован в `service-shell`: SQL-репозиторий, команды и HTTP-маршрут `/api/service/crm`. Это работающий локально проверенный контур, **ещё не подключённый к публичному демоинтерфейсу или рабочим кабинетам**. Данные из localStorage автоматически на сервер не импортируются.

## Доступ и хранение

Повторно используются существующие `getSql()` и Better Auth приложения. В разработке — PGLite; для production маршрут требует настроенный PostgreSQL (`DATABASE_URL`) и отвергает временное PGLite-хранилище. Сессия проверяется через `getSessionUser()` без общего `DEV_USER_ID`. Само наличие этой авторизации **не даёт** прав к данным или кабинетам основного Worker.

Миграция `migrations/0002_service_crm.sql` добавляет три таблицы: пространство со снимком CRM и версией, членство с ролью/отзывом, журнал команд с автором и ключом повтора. Она применяется существующим механизмом миграций, без новых пакетов/облачных ресурсов. В production миграция не запускалась.

Пространства/членство пока создаются доверенным серверным provisioning-процессом; публичной команды выдачи прав нет. Таблицы не содержат демо-сидов. Подключение входа клиентов Cantor, выдача пространства при оплате и сопоставление с проектом/Авито из основного Worker — следующий обязательный этап. Действующие `at:team`/`atAuth` изучены; ключ команды, глобальный пароль панели и токены кабинетов не копируются в браузер и не используются как общий клиентский доступ.

Роли этого среза: `owner` — владелец пространства, `curator` — назначенный сотрудник, `viewer` — только чтение. Это роли CRM, не автоматическое назначение полномочий из трекера. Проверка `workspaceId + userId + active` выполняется при чтении и снова в атомарной записи. Чужое и отсутствующее пространство возвращают одинаковый `404`.

## HTTP

`GET /api/service/crm?workspaceId=<id>` возвращает `{ revision, state }` только действующему участнику. Все суммы снимка — целые копейки RUB.

`POST` на тот же URL, `Content-Type: application/json`:

```json
{
  "revision": 0,
  "requestId": "client-generated-unique-key",
  "command": {
    "type": "record_payment",
    "studentId": "known-student-id",
    "amountMinor": 123450,
    "currency": "RUB",
    "paidAt": "2026-11-16T10:00:00Z"
  }
}
```

Поддержаны `create_lead`, `book_appointment`, `reschedule_appointment`, `appointment_outcome`, `record_payment` (точные поля — `server/commands.ts`). Ручная заявка пока может иметь только неизвестный источник `adId: null`: произвольную чужую атрибуцию API не принимает. Результат встречи проверяется по серверному времени; будущую оплату внести нельзя. ID объектов и журнал событий формирует сервер. Это **учёт поступлений ученика**, а не банковское списание или подписка Cantor. API возвратов в этом срезе не опубликовано.

Успех: `{ revision, state, replayed, mutationRevision }`. Версия проверяется в SQL, снимок и квитанция/аудит изменяются одним statement с CTE. При ошибке квитанции снимок откатывается. Членство блокируется `FOR SHARE` на время записи; нет mutex в памяти процесса и нет обещания атомарности KV.

- `409 revision_conflict`: вернётся актуальный доступный снимок; клиент обязан обновить данные и явно повторить намерение с новой версией. Автоматически перезаписывать состояние нельзя.
- Повтор того же `requestId`, автора и нормализованной команды возвращает успех без второго изменения; версия запроса при повторе может быть старой. Возвращается свежий снимок и исходная `mutationRevision`.
- Повтор ключа с другим автором/содержимым: `409 idempotency_conflict`.
- `422 invalid_transition`: окно занято, встреча не завершилась, объект отсутствует и другие предметные ошибки; `400 invalid_command`: неверная структура.
- Нужна действительная сессия (`401`), право записи (`403`), подходящее членство (`404`). Отозванное право не восстанавливается повтором старой команды.
- Origin и Fetch Metadata защищают от соседнего/чужого браузерного источника. Ответы `no-store`, без CORS-доступа и внутренних SQL-ошибок. Размер тела одной команды ограничен 16 KiB; это транспортная защита, не квота подписки или числа записей.

## Доказательства и пределы

`npm run test:service:server`: HTTP-контракт на настоящих Request/Response и SQL PGLite, включая две параллельные команды, конфликт одного окна, безопасный повтор, разные пространства, отзыв/понижение роли, откат при сбое аудита и закрытие/повторное открытие файловой базы. Отдельно проверен реальный маршрут через Vite: без сессии — 401. Сборка TanStack Start/Nitro проходит.

Эти тесты не являются нагрузочным прогоном нескольких production-процессов на PostgreSQL. Перед подключением клиентов нужны интеграционная проверка на выбранном постоянном PostgreSQL, provisioning/вход, UI для конфликтов и переключение источника данных. Публичный статический preview Worker по-прежнему не имеет базы/секретов и возвращает 503 на `/api/*`.
